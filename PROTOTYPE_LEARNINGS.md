# Post-Prototype Learnings: Preventing Metric Counter and Uptime Resets Across Policy Rollouts (Tab 3)

## 1. Executive Summary

We prototyped and empirically validated the **Tab 3** proposal (`tango_onepager_3_gboc_reload_continuity.md`) in `components/google-built-opentelemetry-collector/provider/googlecontrolplaneprovider` (`v0.162.0`):
1. **Diff-Gated `confmap.WatcherFunc` in `googlecontrolplaneprovider`** (`provider.go:243-411`): Subscribes to `googlepolicy.RegisterWatcherChannel()`, re-evaluates `evaluateActivePolicySet`, compares the synthesized `confmap` against `p.lastConfMap` via `reflect.DeepEqual`, and suppresses `watcher(&confmap.ChangeEvent{})` when only `PolicyClassTransformation` policies (`LogFilterPolicy`, `MetricFilterPolicy`, `TraceFilterPolicy`) change.
2. **Upstream Partial Receiver Reload Feature Gates** (`provider.go:42-47, 115-123`): Enables `service.partialReload` and `service.partialReloadReceivers` alongside `confmap.enableMergeAppendOption` in `newProvider`.

Across end-to-end `otelcol.Collector` verification (`reload_continuity_test.go`, `provider_test.go`), the prototype eliminated all collector reloads on `LogFilterPolicy` rollouts (`0` reloads) and executed in-place `Service.UpdateReceivers` on `SourcePolicy` rollouts (`partial_reloads = 2, full_restarts = 0`), keeping `otelcol_exporter_sent_log_records` (`5 -> 8 -> 18 -> 23`), `otelcol_receiver_accepted_log_records{receiver="otlp/source_a"}` (`5 -> 10 -> 14 -> 16`), `otelcol_receiver_accepted_log_records{receiver="otlp/source_b"}` (`6 -> 9`), and `otelcol_process_uptime` (`0.186s -> 0.286s -> 0.486s -> 0.686s`, unchanged `StartTimestamp`) strictly monotonic.

At the same time, building and running the real collector uncovered **four high-value empirical findings** that refine the companion design doc (`tango_onepager_3_gboc_reload_continuity.md`).

## 2. What Worked vs. What Surprised Us

### 2.1 What Worked as Designed
- **Zero-Reload Transformation Policy Rollouts (`Milestone 1` & `Milestone 2 Step 1`)**:
  - Because `googlepolicyprocessor` (`processor.go:52-109`) independently subscribes to `googlepolicy.RegisterWatcherChannel()` and hot-swaps its `Evaluator` in memory, transformation policies contribute zero keys to `googlecontrolplaneprovider`'s synthesized `confmap`.
  - Diff-gating `watcher(&confmap.ChangeEvent{})` in `googlecontrolplaneprovider` completely suppresses collector reloads on filter/transform rollouts (`reloads = 0`), whereas an unconditional `WatcherFunc` in Baseline triggers a full `Service` restart and resets `otelcol_exporter_sent_log_records` from `5` to `3`.
- **Cache-and-Consume `pendingConfMap` Across `Resolver.Resolve` (`provider.go:246-275, 344-352`)**:
  - When `watcher(&confmap.ChangeEvent{})` fires on a `SourcePolicy` change, `confmap.Resolver.Resolve` immediately closes the previous `Retrieved` handle (`stopPolicyWatcher`) and calls `Provider.Retrieve(ctx, uri, mr.onChange)` again.
  - Caching the diff-evaluated `pendingConfMap` (`pendingRevID`, `hasPending`) and consuming it once in `retrieveAndWatch` prevents double-evaluating the active policy set and prevents emitting duplicate `gcp.policy.evaluate.error` events (`event.go`), while still spawning a fresh watcher goroutine and attaching `confmap.WithRetrievedClose(p.stopPolicyWatcher)` on every `Retrieve` call.

### 2.2 What Surprised Us (Empirical Discoveries)

1. **Positive Surprise — Modified Receiver Instance Counters Do NOT Reset Under `Service.UpdateReceivers` (`Milestone 2 Step 3`)**:
   - **Mental Model / Design Doc Assumption**: `tango_onepager_3_gboc_reload_continuity.md:74` (*Upfront Trade-Offs #1*) assumed that when `Service.UpdateReceivers` stops and recreates a modified receiver instance (e.g., `otlp/source_b` changing its endpoint port), that specific receiver's counter (`otelcol_receiver_accepted_log_records{receiver="otlp/source_b"}`) would reset to `0`.
   - **Empirical Reality**: In `TestReloadContinuity_Prototype_PreservesCountersAndUptime` Step 3 (`reload_continuity_test.go:839-882`), when `Service.UpdateReceivers` stopped `otlp/source_b` on port 1 and recreated `otlp/source_b` on port 2, `otelcol_receiver_accepted_log_records{receiver="otlp/source_b"}` advanced monotonically from **`6 -> 9`** with the exact same `StartTimestamp` (`recvB2.StartTimestamp == recvB3.StartTimestamp`)!
   - **Root Cause**: Because `srv.meterProvider` is preserved across `Service.UpdateReceivers` (`service.go:260-282`), when the newly constructed `otlp/source_b` receiver calls `meter.Int64Counter("otelcol_receiver_accepted_log_records")`, the OpenTelemetry Go Metrics SDK (`go.opentelemetry.io/otel/sdk/metric`) deduplicates synchronous instruments within the same `Meter` scope and returns the **existing underlying instrument**, preserving cumulative counter state for `{receiver="otlp/source_b", transport="grpc"}`.

2. **Critical Boundary Condition — Upstream `receiversOnlyChanged` Requires Stable Pipeline Keys in `service::pipelines` (`Milestone 2 Step 2 vs. Step 4`)**:
   - **Mental Model / Design Doc Assumption**: `tango_onepager_3_gboc_reload_continuity.md:34, 64` stated that enabling `service.partialReload` + `service.partialReloadReceivers` eliminates full service reloads across 100% of `SourcePolicy` rollouts (*"Receivers Added / Modified / Removed"*).
   - **Empirical Reality**: Upstream `receiversOnlyChanged` (`otelcol/config_diff.go:161-168`) checks `len(old.pipelines) != len(cur.pipelines)` and requires every pipeline key (`pid`) in `service::pipelines` to already exist in `old.pipelines`:
     - **Case B1 (Shared Pipeline Key — `Step 2`)**: When multiple `SourcePolicy` instances emit their receiver IDs into the **shared pipeline key** `service::pipelines::logs` (merged via `confmap.enableMergeAppendOption` into `service::pipelines::logs::receivers: [otlp/source_a, otlp/source_b]`), `len(old.pipelines) == len(cur.pipelines)` holds (`[logs, logs/default_self_metrics, metrics/default_self_metrics]`), and `Service.UpdateReceivers` hot-adds `otlp/source_b` with **zero full restarts** (`exporter_sent: 8 -> 18`).
     - **Case B2 (New Pipeline Key — `Step 4`)**: When a `SourcePolicy` introduces a **new pipeline key** (`service::pipelines::logs/source_c`), OR on the `0 -> 1` transition when the very first customer log `SourcePolicy` is added (`provider.go:489-690` only synthesizes `service::pipelines::logs` when at least one `SourcePolicy` returns a non-nil `LogsPipelines`), `len(old.pipelines) != len(cur.pipelines)` is `true`, and `receiversOnlyChanged` returns `false`, falling back to a full service reload (`exporter_sent` resets from `23` to `2`).

3. **Newly Uncovered P0 Production Hazard — `BuiltInSelfMetricsPolicy` Loopback Causes `Service.Shutdown` to Fail During Full Collector Reloads (`TestSelfMetricsLoopback_DirectFullReloadFailsOnShutdown`)**:
   - **Empirical Reality**: `BuiltInSelfMetricsPolicy` (`selfmetrics_policy.go:140-173`) configures the Collector's internal `MeterProvider` (`PeriodicMetricReader`) and `LoggerProvider` (`BatchLogRecordProcessor`) to push OTLP gRPC telemetry over loopback (`http://localhost:27610`) to `receivers.otlp/default_self_metrics` (`127.0.0.1:27610`), which is a receiver inside the **same `service.Service` instance's pipeline graph**.
   - During **any** full Collector reload (`otelcol.Collector.reloadConfiguration`, `collector.go:310-321`), upstream `Service.Shutdown(ctx)` (`service.go:289-322`) shuts down components in this hardcoded order:
     1. `srv.host.Pipelines.ShutdownAll(ctx)` (`service.go:300`) — **stops `otlp/default_self_metrics` (`127.0.0.1:27610`)**.
     2. `srv.meterProvider.Shutdown(ctx)` (`service.go:315`) — flushes `PeriodicMetricReader` to `localhost:27610`, which fails with `dial tcp 127.0.0.1:<port>: connect: connection refused` (after blocking up to `timeout := 30000` = 30s in production `selfmetrics_policy.go:124`!).
   - Because `col.reloadConfiguration(ctx)` (`collector.go:313-315`) checks `if err := col.service.Shutdown(ctx); err != nil { return fmt.Errorf("failed to shutdown the retiring config: %w", err) }`, **any full reload on an unproxied `BuiltInSelfMetricsPolicy` loopback topology fatally aborts `col.Run(ctx)` and terminates the Collector process!**
   - Our prototype avoids calling `col.service.Shutdown(ctx)` on `LogFilterPolicy` rollouts (`0` reloads) and `SourcePolicy` Case B1/Case A rollouts (`Service.UpdateReceivers`), preventing this crash on those paths.

## 3. Design-Doc Discrepancies & Recommended Spec Updates (`tango_onepager_3_gboc_reload_continuity.md`)

| Section / Line in `tango_onepager_3_gboc_reload_continuity.md` | Current Claim in Draft One-Pager | Empirical Prototype Finding | Recommended Spec Update |
| :--- | :--- | :--- | :--- |
| **Context and Motivation #2** (`line 17`) & **Alternatives Considered (`Alt 2`)** (`line 86`) | Claims `SelfMetricsPolicy` (`selfmetrics_policy.go:140-157`) converts `otelcol_process_uptime` from a cumulative counter to a gauge via OTTL (`convert_sum_to_gauge() where metric.name == "otelcol_process_uptime"`). | In `v0.162.0` (`selfmetrics_policy.go:228-248`), `transform/default_self_metrics` only prefixes metric names with `"agent.googleapis.com/agent/"` and does **not** call `convert_sum_to_gauge()`. `otelcol_process_uptime` is exported as a cumulative `Sum` (`Float64ObservableCounter`), whose `StartTimestamp` and value still reset to `~0s` (`0.288s -> 0.083s`) on every full `Service` restart. | Update lines 17 and 86 to state that in `v0.162.0`, `otelcol_process_uptime` is a cumulative `Sum` counter (`Float64ObservableCounter`) that resets its `StartTimestamp` and value to `0` on full `Service` recreation (`proctelemetry.RegisterProcessMetrics`, `process_telemetry.go:65`). |
| **Proposed Design** (`lines 34, 47-53, 64`) | Claims enabling `service.partialReload` + `service.partialReloadReceivers` handles 100% of `SourcePolicy` additions/removals without full reloads. | Upstream `receiversOnlyChanged` (`otelcol/config_diff.go:161-168`) requires `len(old.pipelines) == len(cur.pipelines)` and identical pipeline keys (`pid`). Adding/removing a `SourcePolicy` uses `Service.UpdateReceivers` **if and only if** `SourcePolicy.LogsPipelines()` emits into an already-existing shared pipeline key (`service::pipelines::logs`). Adding a new pipeline key (or the `0 -> 1` transition when `service::pipelines::logs` is first created) triggers a full reload. | Add a design requirement that all Tango `SourcePolicy` drivers must emit into the shared `service::pipelines::logs` pipeline key (using `confmap.enableMergeAppendOption`), and either pre-seed `service::pipelines::logs` with a no-op receiver on startup (so `0 -> 1` customer `SourcePolicy` does not add a pipeline key) or extend upstream `UpdateReceivers` to support adding/removing receiver-only pipelines. |
| **Upfront Trade-Offs #1** (`line 74`) | Claims *"Modified Receiver Instance Counters Still Reset"* when `Service.UpdateReceivers` stops and recreates a modified receiver (`filelog/policy_a`). | In `v0.162.0`, because `srv.meterProvider` is preserved across `Service.UpdateReceivers`, the OTel Go Metrics SDK returns the same underlying synchronous `Int64Counter` instrument for the recreated receiver ID (`otlp/source_b`), **preserving** `otelcol_receiver_accepted_log_records{receiver="otlp/source_b"}` (`6 -> 9` monotonic, identical `StartTimestamp`)! | Update Upfront Trade-Off #1 to note that synchronous `MeterProvider` counters (`otelcol_receiver_accepted_log_records`, `otelcol_receiver_refused_log_records`) are **also preserved** for modified receiver IDs because `srv.meterProvider` is retained across `Service.UpdateReceivers`. |
| **Root Cause / Proposed Design** (`lines 24-28`) | Assumes a full `Service` reload in GBOC merely resets counters and restarts exporters. | `TestSelfMetricsLoopback_DirectFullReloadFailsOnShutdown` proved that `BuiltInSelfMetricsPolicy`'s OTLP gRPC loopback (`PeriodicMetricReader -> localhost:27610 -> otlp/default_self_metrics`) causes `col.service.Shutdown(ctx)` to fail in `srv.meterProvider.Shutdown(ctx)` (`connection refused` after a 30s timeout) because `Pipelines.ShutdownAll` (`service.go:300`) stops `otlp/default_self_metrics` before `meterProvider.Shutdown` (`service.go:315`), fatally crashing `col.Run(ctx)` on any full reload! | Add a P0 warning in *Root Cause* documenting the `BuiltInSelfMetricsPolicy` loopback shutdown ordering bug during full reloads, and recommend either switching internal self-metrics ingestion to an in-memory / Prometheus pull bridge or ignoring loopback flush errors after `Pipelines.ShutdownAll`. |

## 4. Productionization Gap Ledger

| Gap ID | Category | Prototype Shortcut / Limitation | Production Hardening Requirement |
| :--- | :--- | :--- | :--- |
| **G1** | **Self-Metrics Loopback Shutdown Ordering (`selfmetrics_policy.go`)** | In `reload_continuity_test.go`, `startSelfMetricsLoopbackProxy` absorbs the `connection refused` error during `srv.meterProvider.Shutdown(ctx)` when testing full reloads (Baseline & Step 4), while `TestSelfMetricsLoopback_DirectFullReloadFailsOnShutdown` demonstrates the raw crash. | Before enabling full collector reloads in production (`Case B2` or future `DestinationPolicy` changes), decouple `BuiltInSelfMetricsPolicy` from self-loopback OTLP gRPC push on shutdown (e.g., use an in-memory/pull reader or suppress `connect: connection refused` on retiring loopback telemetry flushes after `Pipelines.ShutdownAll`). |
| **G2** | **`0 -> 1` Customer `SourcePolicy` Pipeline Key Transition** | In `TestReloadContinuity_Prototype_PreservesCountersAndUptime`, the collector starts with 1 initial customer log source (`otlp/source_a` in `service::pipelines::logs`), so adding `otlp/source_b` (Step 2) keeps `service::pipelines` keys unchanged (`len(old.pipelines) == len(cur.pipelines)`). | In `googlecontrolplaneprovider.evaluatePolicySet` (`provider.go:489-690`), always synthesize `service::pipelines::logs` (e.g., with a built-in no-op receiver when zero customer `SourcePolicy` instances exist) so that rolling out the *first* customer `SourcePolicy` (`0 -> 1`) also takes the `Service.UpdateReceivers` partial reload path instead of adding a new pipeline key. |
| **G3** | **Process-Level `startTimeUnixNano` in Upstream `proctelemetry`** | Out of scope for the GBOC repo prototype (`go.opentelemetry.io/collector/service@v0.162.0` is an external Go module dependency). | Upstream a 3-line patch to `open-telemetry/opentelemetry-collector` (`service/internal/proctelemetry/process_telemetry.go:65`) to capture `processStartTimeUnixNano` once at package initialization so `otelcol_process_uptime` never resets even when a full `Service` reload occurs (Step 4). |
| **G4** | **Global Feature Gate Mutation in `newProvider`** | `newProvider` (`provider.go:115-123`) mutates `featuregate.GlobalRegistry()` to enable `service.partialReload` and `service.partialReloadReceivers` (matching existing `confmap.enableMergeAppendOption` behavior). | Set these feature gates once in GBOC's main distribution entrypoint (`cmd/otelcol-google`) or component manifest rather than mutating the global registry inside `newProvider`. |
