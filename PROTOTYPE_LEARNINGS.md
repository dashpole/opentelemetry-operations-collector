## 1. Hypothesis Verdict: **CONFIRMED (with Critical Design Doc Refinement for `body["details"]`)**

1. **Engine Hypothesis (`LogTransformPolicy` & `body_field` in `pkg/googlepolicy` + `googlepolicyprocessor`) — CONFIRMED**:
   - Extending `LogFieldSelector` with `AttributePath body_field = 6` (`proto/policy/v1alpha1/log_filter_policy.proto`) and implementing `LogTransformPolicy` (`LogAddAction`, `LogRemoveAction`, `LogRenameAction`, `LogRedactAction` in `proto/policy/v1alpha1/log_transform_policy.proto` and `pkg/googlepolicy/logtransform`) integrates cleanly with `googlepolicyprocessor`.
   - `googlepolicyprocessor.Evaluator` enforces the `go/tango-preview-policies` Double-Applied Filtering and deterministic 4-stage ordering contract:
     `Pass 1 Pre-Transform LogFilterPolicy -> Stage 1 (rename) -> Stage 2 (add) -> Stage 3 (remove) -> Stage 4 (redact) [tie-broken lexicographically by Policy ID] -> Pass 2 Post-Transform LogFilterPolicy`, verified by `TestEvaluator_LogTransformStageOrderingAndDoubleFilter` (`evaluator_test.go:1177-1345`).
2. **WEF Empirical Payload & Live Export Hypothesis (`raw: false` and `raw: true`) — CONFIRMED**:
   - Parsing realistic pre-rendered German (`Culture='de-DE'`) WEF XML payloads for Windows Security Event `4624` (`4,869 B` XML containing `2,829 B` of `<RenderingInfo>` and `2,040 B` of `<Event><System>...</System><EventData>...</EventData></Event>`) and Event `4688` (`3,840 B` XML containing `2,278 B` of `<RenderingInfo>` and `1,562 B` of non-`RenderingInfo` XML) through the verbatim upstream `pkg/stanza@v0.160.0/operator/input/windows` + `adapter/converter.go` pipeline (`internal/stanzawindows`) proved:
     * **Structured Full Strip (`1C`: `raw: false` + 3 `LogRemoveAction` rules on `["rendering_info"]`, `["message"]`, and `["details"]`)**: Reduces serialized OTLP `plog.Logs` size from **`6,919 B -> 1,455 B` (`-79.0%`, `5,464 B` saved)** on Event `4624` and from **`5,470 B -> 1,198 B` (`-78.1%`, `4,272 B` saved)** on Event `4688`, with **`0 B/op` and `0 allocs/op`** incremental heap overhead (`+1,135 ns/op` vs. `1A` No-Op baseline), while preserving 100% of `<System>` (`event_id.id`, `provider.name`, `computer`, `channel`, `record_id`, `system_time`) and all **27** (Event `4624`) / **15** (Event `4688`) `<EventData>` keys.
     * **Raw XML Redact (`2B`: `raw: true` + `LogRedactAction` on `LOG_RECORD_FIELD_BODY` with `regex: "<RenderingInfo[^>]*>[\\s\\S]*?</RenderingInfo>"`)**: Strips **100% of the `<RenderingInfo>` block** (`2,829 B` on Event `4624`, `2,278 B` on Event `4688`), reducing total serialized OTLP `plog.Logs` size from **`4,910 B -> 2,081 B` (`-57.6%`)** on Event `4624` and from **`3,881 B -> 1,603 B` (`-58.7%`)** on Event `4688`, while leaving 100% valid `<Event><System>...</System><EventData>...</EventData></Event>` XML (`2,040 B` and `1,562 B`) with all **27** and **15** `<EventData>` elements intact.
     * **Live Cloud Logging Export (`dashpole-dev`)**: `TestWEFRenderingInfo_LiveCloudLoggingExport` exported 4 transformed WEF records (2 structured `1C` + Event ID enrichment `event.action = "user-login" | "process-created"`, and 2 raw XML `2B`) over ECP mTLS (`telemetry.mtls.googleapis.com:443`) to `dashpole-dev` with `rejected_log_records = 0`, verified via `gcloud logging read` (`insertId`s `1m01ut3f4mippy`, `1m01ut3f4mippz`, `1m01ut3f4mipq0`, `1m01ut3f4mipq1`).

## 2. Surprises & Unexpected Findings

1. **Surprise #1 — Double-Duplication in Structured Mode (`1A`) & Why `remove(body_field(["details"]))` Is Mandatory (`1B` vs. `1C`)**:
   - In upstream `pkg/stanza@v0.160.0/operator/input/windows/xml.go:88-149` and `security.go:10-59`, when `e.RenderingInfo != nil` and `<Channel>Security</Channel>` (the source workstation channel preserved inside WEF event XML even when read from `ForwardedEvents`), `formattedBody` calls `parseSecurity(rawMessage)`:
     * `parseSecurity` extracts only the first line (`39 B` `"Ein Konto wurde erfolgreich angemeldet."` on Event `4624`, `56 B` serialized proto) into `body["message"]`, and parses the remaining `~98%` of the German `<RenderingInfo><Message>` (`2,492 B` UTF-8) into a nested map `body["details"]` (`2,669 B` serialized proto map on Event `4624`, `2,034 B` on Event `4688`), including `body["details"]["Additional Context"]` (`[]string` of multi-paragraph German explanatory text).
     * Simultaneously, `formattedBody` (`xml.go:147-149`) stores the full `e.RenderingInfo.asMap()` in `body["rendering_info"]` (`2,739 B` serialized proto map on Event `4624`).
   - Consequently, in `raw: false` mode (`1A`), the German `<RenderingInfo><Message>` is stored **twice** inside `LogRecord.Body()`, inflating Event `4624` from `4,869 B` raw XML to **`6,919 B` (`+42.1%`)**.
   - If a policy only strips `body_field(["rendering_info"])` and `body_field(["message"])` (`1B`, as currently drawn in the Companion Design Doc's ASCII diagram at `tango_onepager_5_wef_rendering_info_stripping.md:48-49`), Event `4624` only shrinks by `40.4%` (`6,919 B -> 4,124 B`), leaving **`2,669 B` (`64.7%` of the remaining payload)** of German prose in `body["details"]`.
   - **Actionable Design Doc Fix**: In `tango_onepager_5_wef_rendering_info_stripping.md`, the ASCII diagram (`lines 48-57`) currently lists only 2 `LogRemoveAction` rules (`["rendering_info"]` and `["message"]`) and estimates a `~500 B` post-strip size, while the prose bullet at `line 69` parenthetically treats `["details"]` as optional (`(plus ["details"] if present)`). Both should be updated to state that all **three** `LogRemoveAction` rules (`["rendering_info"]`, `["message"]`, AND `["details"]`) are mandatory for `<Channel>Security</Channel>` events, and to cite the empirically measured `1,198–1,455 B` structured OTLP size (`-78.1%` to `-79.0%`) and `1,603–2,081 B` raw XML OTLP size (`-57.6%` to `-58.7%`).
2. **Surprise #2 — Top-Level Short Labels Copied from `e.RenderingInfo` by `formattedBody`**:
   - In `xml.go:88-102`, `formattedBody` overwrites top-level `level`, `task`, `opcode`, and `keywords` with `e.RenderingInfo.{Level,Task,Opcode,Keywords}` whenever non-empty. Thus after `1C` removes `["rendering_info"]`, `["message"]`, and `["details"]` (removing 100% of the multi-KB `<Message>` prose), top-level `body["level"]` (`"Informationen"`), `body["task"]` (`"Anmeldung"` / `"Prozesserstellung"`), `body["opcode"]` (`"Info"`), and `body["keywords"]` (`["Überwachung erfolgreich"]`) retain those short localized labels (`~85 B` total). Because `event_id.id` (`4624`/`4688`), `provider.name` (`"Microsoft-Windows-Security-Auditing"`), and `event_data` are 100% intact, downstream CBN/UDM parsers that key off `(Provider.Name, EventID.ID, EventData)` are unaffected.
3. **Surprise #3 — `compileRename` Destination-First Ordering (`G2M1-P0-1`)**:
   - During Gate 2 (Milestone 1) adversarial review, we caught that calling `fromTarget.remove(ctx)` before `toTarget.set(ctx, ...)` in `LogRenameAction` would lose the source attribute if `toTarget.set` failed (e.g., renaming a `log_attribute` into a `body_field` when `LogRecord.Body()` is `ValueTypeStr`, or self-renaming `from == to`). Checking `proto.Equal(rn.GetFrom(), rn.GetTo())` and executing `toTarget.set` before `fromTarget.remove` guarantees zero data loss under fail-open semantics.
4. **Surprise #4 — Single-Pass RE2 Execution Cuts `LogRedactAction` CPU Cost by 2.0x**:
   - Initially, `compileRedact` called `if !re.MatchString(orig)` before `re.ReplaceAllString(orig, replacement)`, causing two full RE2 passes over the `4,869 B` multi-line XML (`223,490 ns/op`). Because Go's standard library `regexp.ReplaceAllString(orig, replacement)` returns `orig` without allocating when no match is found, calling `re.ReplaceAllString` directly and checking `replaced != orig` cut `2B_RawXMLRedact_Regex` latency in half to **`111,961 ns/op`** (`+110,873 ns/op` over `2A` baseline).
5. **Surprise #5 — Structured `1C` Outperforms Raw XML `2B` in Both Wire Size and CPU**:
   - Even after `2B` strips 100% of `<RenderingInfo>` from raw XML (`4,910 B -> 2,081 B`), `1C` (`1,455 B`) is **`30.1%` smaller on the wire** than `2B` (`2,081 B`) because `1C` encodes `event_data` as compact protobuf map entries rather than verbose `<Data Name='...'>...</Data>` XML tags (`2,040 B`), and `1C`'s 3 `O(1)` map deletes (`+1.1 µs`, `0 B/op`, `0 allocs/op`) are **`~98x` faster** than `2B`'s RE2 multi-line regex replacement (`+110.9 µs`, `+4,157 B/op`, `+4 allocs/op`).

## 3. Production Readiness Gap Analysis

| Dimension | Prototype State (`proto/tango-tab5-wef-renderinginfo-strip`) | Production Requirement |
| :--- | :--- | :--- |
| **Scale & Concurrency** | `LogTransformPolicy` pre-compiles `CompiledMatcher` slices, `mapTarget` path selectors, and RE2 `regexp.Regexp` instances at policy load time (`NewPolicyFromProto`), making `TransformLog(ctx)` stateless and goroutine-safe across concurrent `ConsumeLogs` calls. | Benchmark high-cardinality multi-policy sets (`50+` `LogTransformPolicy` rules per `Evaluator`) and verify zero lock contention under concurrent worker goroutines. |
| **Error Handling, Retries, & Observability** | `Evaluator.TransformLogs` tracks `PolicyStats` (`MatchedRecords`) for `LogFilterPolicy` rules; `LogTransformPolicy` fails open (`return false`) on type mismatches or missing paths without panicking. | Expose OpenTelemetry processor self-observability metrics (`otelcol_googlepolicy_log_transform_mutated_records_total{policy_id,stage}`) via `internal/metadata` telemetry builder so operators can monitor WEF stripping rates in Cloud Monitoring. |
